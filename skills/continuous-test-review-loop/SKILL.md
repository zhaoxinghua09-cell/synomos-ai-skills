# continuous-test-review-loop（实测-复盘-改进循环）

**定位**：一个把"测试 → 复盘 → 改进 → 复测"固化为可重复节奏的方法论 + 模板工具。它不替你写代码，而是给你一套能直接套用的清单、模板和闭环纪律，让"上线后持续验证"和"团队复盘习惯"真正落地。

**何时用**：方案/功能已上线或待上线，需要建立常态化验证节奏；团队想沉淀复盘机制；要把每轮验证证据归档以便审计追溯。
**何时不用**：一次性临时验证且无复用需求；纯医疗/临床决策场景（本技能非医疗器械、非医疗软件，详见铁律）；仅需单次代码 review 而非持续循环。

---

## 一、能力边界

**能做**
- 生成/维护一份「固定测试清单」（功能/性能/安全/回归分类）。
- 按「复盘四问」模板结构化每轮结论。
- 驱动「提出→评审→实施→验证→归档」改进闭环。
- 把每轮报告按规范写入方案池（artifact pool）做可审计证据链。
- 多语种（中/英/日/韩/西/法/德/阿）输入输出，跟随用户语言。

**不能做（边界）**
- 不执行真实测试：它产出清单与结论，**不代替**测试框架/CI 运行用例。
- 不修改你的代码仓库：只给改进项与 owner，不改文件。
- 不连接外部系统跑数据：除非通过技能依赖显式授权（见第八章）。
- 不做医疗诊断/疗效判定：属通用方法论，非医疗器械软件。
- 无网络依赖也能工作：纯文档型技能，离线可用，运行稳定性取决于底层 AI。

**技术约束**
- 输入规模：单次建议 ≤ 1 个方案/模块；多模块请分批。
- 性能：纯文本推理，无超时/重试机制（见第十章稳定性说明）。
- 集成边界：可与 `a3-law-operational`、`ai-governance-audit-chain` 协作，但不自动调用它们。

## 二、输入约束与输出承诺

**输入约束**
- 必填：①待验证对象描述（方案名/模块/变更点）；②验证目标或验收标准。
- 选填：历史测试清单、上轮复盘、已有证据链接、轮次号。
- 格式：自由文本、Markdown、或 CSV 均可；非结构化亦可，由技能结构化。
- 拒收：含机密凭据的原始配置（见第八章）；非中文时自动跟随语言。

**输出承诺（每轮必有）**
1. `测试清单`：含编号/类型/预期/实际/通过(Y/N)/证据/负责人/轮次。
2. `复盘纪要`：按四问模板产出，含根因与改进项。
3. `改进项`：每条带 owner、截止、可验证标准。
4. `复测结论`：改进后是否通过，未通过则回流下一轮。
5. `入池记录`：本轮报告摘要 + 溯源指纹，供审计。

**质量承诺**：不编造测试结果；未实测的项标「待验证」而非「通过」；结论可追溯到具体证据。

## 四、常见错误与反模式（FAQ + 高频 Q&A）

**反模式**
- ❌ 只测一遍就归档：循环价值在"复测"，单轮不是闭环。
- ❌ 改进项无 owner/无截止：会烂尾，必须可验证。
- ❌ 把"未测"写成"通过"：伪造证据，违反铁律。
- ❌ 复盘写成流水账：须落到根因 + 改进项。
- ❌ 清单无限膨胀：固定清单应稳定，新增需评审。

**高频 Q&A**
- Q：模板要自己填吗？ A：技能生成骨架，你补实际结果/证据；它不替你跑测试。
- Q：多模块怎么办？ A：分批，每模块一轮，报告各自入池。
- Q：和现有 CI 冲突吗？ A：不冲突，本技能产出清单可喂给 CI 用例。
- Q：多久一轮？ A：节奏由你定（建议周/双周），技能只管闭环纪律。
- Q：医疗能用吗？ A：不能做诊断/疗效，通用复盘方法论可参考但须免责。

## 五、标准 SOP（步骤表）

| 步骤 | 动作 | 产出 | 判停条件 |
|---|---|---|---|
| 1. 立项 | 明确待验证对象 + 验收标准 | 对象卡 | 缺验收标准则退回补 |
| 2. 建清单 | 按四类生成固定测试清单 | 测试清单 v1 | 清单非空且分类完整 |
| 3. 执行 | 你跑测试，填实际结果/证据 | 带结果的清单 | 全部项标 Y/N |
| 4. 复盘 | 按四问模板结构化结论 | 复盘纪要 | 含根因 + 改进项 |
| 5. 改进 | 改进项派 owner/截止 | 改进项列表 | 每条可验证 |
| 6. 复测 | 改后重跑相关项 | 复测结论 | 通过→7；未过→回 3 |
| 7. 入池 | 报告摘要 + 指纹归档 | 入池记录 | 可审计追溯完成 |

> 循环不终止于"通过"，而终止于"证据入池 + 下一轮触发条件明确"。

## 六、关键事实速查

- **四阶段**：测试 → 复盘 → 改进 → 复测（闭环，非瀑布）。
- **测试清单字段**：编号｜类型(功能/性能/安全/回归)｜预期｜实际｜通过(Y/N)｜证据｜负责人｜轮次。
- **复盘四问**：①本轮测了啥、结果？②哪环出问题、根因？③改进项是啥、owner/截止？④下轮验证点？
- **改进闭环**：提出 → 评审 → 实施 → 验证 → 归档。
- **报告入池**：每轮摘要 + 溯源指纹，供 `ai-governance-audit-chain` 审计。
- **节奏**：周/双周建议；稳定性依赖底层 AI，无自带重试。
- **语言**：8 种，跟随用户输入语言。
- **非医疗**：通用方法论，非医疗器械/医疗软件。

## 七、铁律（PROHIBITED）

- 🚫 不伪造、不臆造测试结果；未实测标「待验证」。
- 🚫 不跳过复盘直接归档；闭环必须含复盘纪要。
- 🚫 不把任何机密凭据写入对话或报告（见第八章）。
- 🚫 不用于医疗诊断/疗效/临床决策声明。
- 🚫 不修改用户代码仓库或越权调用外部系统。
- 🚫 不对未验证项宣称"通过"以通过审计。
- 🚫 不替代专业合规/法律意见；仅给方法论与模板。

## 九、示例

**场景**：支付模块 v2 上线后持续验证。

1. 对象卡：支付模块 v2｜验收：成功率≥99.9%、P99<300ms、无资损。
2. 测试清单 v1：
   | 编号 | 类型 | 预期 | 实际 | 通过 | 证据 | 负责人 | 轮次 |
   |---|---|---|---|---|---|---|---|
   | T01 | 功能 | 支付成功 | 成功 | Y | ev01 | 甲 | R1 |
   | T02 | 性能 | P99<300ms | 420ms | N | ev02 | 甲 | R1 |
   | T03 | 安全 | 无越权 | 待验证 | — | — | 乙 | R1 |
3. 复盘四问：本轮 3 项中 T02 不达标；根因=并发连接池过小；改进项=扩容连接池(owner 甲/截止周五/验证 P99<300ms)；下轮验证点 T02。
4. 改进闭环：提出→评审(通过)→实施(扩容)→验证(复测 T02)→归档。
5. 复测：R2 中 T02 实测 P99=260ms → 通过 → 入池。T03 补测无越权 → 通过 → 入池。
6. 入池记录：R1+R2 摘要 + 指纹 FP-MX-xxxx，供审计追溯。

## 十、错误处理

本技能为文档型，无代码级异常；以下为用户/AI 侧错误引导：

| 错误码 | 场景 | 处理 |
|---|---|---|
| E1 | 缺验收标准 | 退回步骤 1，请补验收标准再继续 |
| E2 | 输入含明文凭据 | 拒收，提示从保险库读取，不记录值 |
| E3 | 未测项被标通过 | 触发铁律，改标「待验证」并提示 |
| E4 | 改进项无 owner/截止 | 退回步骤 5，补全可验证字段 |
| E5 | 医疗/临床意图 | 拒答主场景，给通用方法论 + 免责 |

**稳定性说明**：运行完全依赖底层 AI，技能本身无重试/超时/容错；遇 AI 中断请重发对象卡，清单可从最近入池记录续接。
