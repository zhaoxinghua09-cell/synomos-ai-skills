# 前提验证与配置审计（Premise & Config Audit）

> 发声大使：**诺衡(Krites)@SynomosAI** · 品牌归属 **SynomosAI** · 许可证 **MIT** · 版权 **SynomosAI**
> 本技能是**可操作的方法论手册**，不是概念宣言。照着「五、标准 SOP」即可直接上手。

## 定位 + 何时用 / 何时不用

**它是什么**：一套「先验证前提、再审计配置」的双轨检查法，用来在开工前、复盘时、调优时，把"自以为成立"的东西变成"已验证成立"的东西。

**何时用**
- 启动一个新方案 / 新项目前，想确认"我默认接受的那些前提真的成立吗"。
- 工具链、环境、流程跑得别扭，想系统性判断"配置是不是次优、冲突或冗余"。
- 一个方案已经走偏，想复盘"是哪条前提错了 / 哪处配置坑了它"。

**何时不用**
- 纯创意发散、不需要落地执行的头脑风暴（此时过早验证会扼杀灵感）。
- 已有权威事实（如"今天天气"）无需再证伪。
- 医疗诊断、疗效判定、法规强制合规结论——本技能非医疗器械/非医疗软件，不替代专业判断。
- 涉及密钥/凭据明文处理——见「八、输入输出依赖」。

## 一、能力边界

| 维度 | 本技能能做 | 本技能不能做 |
|------|-----------|-------------|
| 前提验证 | 区分事实/假设/预判；用真实参照法证伪；输出风险等级 | 替你做最终业务决策；保证 100% 无遗漏 |
| 配置审计 | 盘点配置项、对照目标函数评分、列改进项 | 自动改你的生产配置；访问无权限的系统 |
| 范围 | 单方案 / 单工具链 / 单环境 | 跨组织治理、法律合规裁定 |
| 输出 | 清单、评分、建议、反例 | 不可执行的"保证书" |

**技术约束**
- 输入规模：单次审计建议 ≤ 50 个前提项、≤ 30 个配置项，超出请分批。
- 不依赖外部网络/API；纯方法论，离线可用。
- 不回显任何密钥、令牌、口令明文（见第八章）。

## 二、输入约束与输出承诺

**输入约束**
- 至少提供：①待验证的前提或待审计的配置清单 ②判断"好/坏"的目标函数（如"上线零故障""月成本<X"）。
- 缺目标函数时，本技能会先用「默认目标函数」假设并**显式标注**为待你确认，不悄悄替你定。
- 输入语言：中文（默认）；其他语言可识别但术语以中文为准。

**输出承诺**
- 前提验证 → 输出「前提验证清单」：每条含 类型(事实/假设/预判)、验证方法、参照源、结论(成立/存疑/推翻)、风险等级(高/中/低)。
- 配置审计 → 输出「配置健康度报告」：总分(0–100)、逐项(次优/冲突/冗余/缺失)、Top3 改进项。
- 一律给"下一步动作"，不给空洞结论。

## 三、触发场景（意图表 + 示例对话）

| 用户意图 | 触发说法（示例） | 触发方式 |
|---------|----------------|---------|
| 开工前验前提 | "开工前我该先验什么？" / "premise check" | 对话触发 |
| 审计工具链配置 | "我的工具链配置是不是次优？" / "config audit" | 对话触发 |
| 复盘走偏 | "这个方案为什么走偏了？" / "复盘假设" | 对话触发 |
| 指令式 | `/premise-and-config-audit 审计我的 CI 配置` | 指令触发 |

**示例对话**
> 用户：我准备把数据库迁到新实例，开工前帮我验下前提。
> 技能：收到。请给我①你默认接受的前提清单（如"新实例性能和旧的一致"），②本次迁移的目标函数（如"停机<5分钟"）。我先用真实参照法逐条证伪。

## 四、常见错误与反模式（FAQ + 高频 Q&A）

**反模式（应避免）**
- ❌ 把预判当事实："用户肯定会喜欢"→ 应标为「预判」并找数据证伪。
- ❌ 只证成不证伪：只找支持证据。→ 必须优先尝试推翻。
- ❌ 审计无目标函数：用"感觉不对"评判。→ 必须显式定义目标函数。
- ❌ 一次塞 100 项：漏检且混乱。→ 分批，≤50 前提。

**高频 Q&A**
- Q：没有数据怎么证伪？A：标「存疑」并给最低可行验证动作（如"问 3 个用户"），不强行结论。
- Q：目标函数谁来定？A：你定；缺失时我用默认并标注待确认。
- Q：审计出的问题要我立刻改吗？A：只列优先级，改不改、何时改由你定。

## 五、标准 SOP（步骤表）

**A. 前提验证 SOP**
| 步 | 动作 | 产出 |
|----|------|------|
| 1 | 列出默认接受的所有前提 | 原始前提池 |
| 2 | 逐条打标：事实 / 假设 / 预判 | 分类后的前提 |
| 3 | 对每条假设/预判，找真实参照源（数据、文档、实验） | 参照记录 |
| 4 | 优先证伪：尝试推翻，记录失败/成功 | 证伪结果 |
| 5 | 输出结论 + 风险等级 + 下一步 | 前提验证清单 |

**B. 配置审计 SOP**
| 步 | 动作 | 产出 |
|----|------|------|
| 1 | 盘点当前配置项（配置、环境变量、流程） | 配置清单 |
| 2 | 明确目标函数 | 评判基准 |
| 3 | 逐项对照：次优/冲突/冗余/缺失 | 问题标记 |
| 4 | 加权评分(0–100) | 健康度总分 |
| 5 | 输出 Top3 改进项 + 动作 | 配置健康度报告 |

**真实参照法（Grounded Reference Method）**：任何前提都必须能指向一个"外部可核验的真实源"，而非内部自洽。找不到源的，标「存疑」。

## 六、关键事实速查

- 前提三类：事实（已核验）/ 假设（待验）/ 预判（推测）。处理成本递增。
- 证伪优先于证成：一条反例 > 十条佐证。
- 配置健康度 = f(目标函数契合度, 冲突数, 冗余度, 缺失度)。
- 风险等级：推翻高影响前提 = 高风险；存疑低影响 = 低风险。
- 缺失目标函数时一律标注「默认假设，待确认」，不静默替代。

## 七、铁律（PROHIBITED）

- 🚫 绝不把预判当作已验证事实输出。
- 🚫 绝不做只证成不证伪的"验证"。
- 🚫 绝不在无目标函数时谎称已客观评判。
- 🚫 绝不回显密钥/令牌/口令明文（见第八章）。
- 🚫 绝不替用户做最终业务/医疗/法律决策。
- 🚫 绝不声称"100% 无遗漏"或出具保证书。

## 八、输入输出依赖（凭据从保险库读，不进对话）

- 本技能本身**不持有任何凭据**，纯离线方法论。
- 若审计对象包含密钥/令牌（如配置文件里的密码）：只报告「存在 / 缺失 / 格式合规」，**绝不回显明文**。
- 如确实需要读取外部凭据来完成审计，须从保险库（如 `credential-vault` / DPAPI 本地保险库）读取，**凭据内容不得进入对话上下文**，仅以"已读取/读取失败"状态参与判断。
- 违反本条即触发「七、铁律」并中止该次审计。

## 九、示例

**示例 1：前提验证**
> 前提："新 API 吞吐是旧版的 2 倍"（预判）
> 参照源：压测报告（真实参照法）
> 证伪尝试：旧版峰值 1k QPS，新版报告 1.8k，未达 2 倍
> 结论：部分推翻 → 风险中 → 下一步：按 1.8k 重算容量余量。

**示例 2：配置审计**
> 目标函数：CI 平均时长 < 10 分钟
> 配置项：并行度=2、缓存未开启、两步重复拉取依赖
> 标记：次优(并行度低)、冗余(重复拉取)
> 评分：62/100 → Top3：开缓存、并行度调 4、去重拉取。

## 十、错误处理

| 情况 | 识别信号 | 处理 |
|------|---------|------|
| 输入缺目标函数 | 未提供评判基准 | 用默认目标函数 + 标注「待确认」，继续 |
| 前提无法证伪 | 无参照源 | 标「存疑」，给最低可行验证动作 |
| 配置项超量 | >50 前提 / >30 配置 | 提示分批，先处理高优先级 |
| 遇到密钥明文 | 输入含 token/password | 立即脱敏，仅报存在性，不回显 |
| 用户要决策替代 | "你帮我定就行" | 拒绝，只给建议与优先级 |
| 矛盾前提 | 两条互相推翻 | 同时标出，要求用户裁决 |

> 所有错误均「降级为指引」而非中断：先给能用的部分，再说明卡点。
