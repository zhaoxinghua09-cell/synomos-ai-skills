# 单一事实源与变更管理（SSOT Content Management）

## 定位 + 何时用 / 何时不用

本技能是一套**声明式内容管理方法论**：把会反复变化、被多处引用的「事实」集中存放在唯一事实库，内容通过引用事实生成，变更事实即全链路生效，从而把返工从「事后救火」前移到「机制前置」。

**何时用**
- 同一段信息（参数、口径、文号、价格、状态）出现在 ≥2 个文档/页面/渠道，且会变化。
- 每次更新都要手动改很多地方、容易漏改。
- 官网、公众号、投标书、培训材料、知识库共享同一批事实。
- 想让 AI/脚本自动按事实生成或同步内容。

**何时不用**
- 一次性、永不复用的草稿或临时笔记。
- 纯创意写作（文案语气、故事），不存在「被多处引用的可变事实」。
- 受监管且必须逐份人工签核、不允许引用生成的法定原件（可引用其「摘要/口径」，但原件另走合规流程）。
- 需要实时强一致事务（如金融交易）——本方法是内容/知识层，不是数据库事务。

---

## 一、能力边界

- **能做的**：识别可变事实、设计事实库字段、定义三层引用关系、给出落地步骤、产出变更影响清单、复盘返工根因。
- **不能做的（明确禁区）**：
  - 不替代业务决策：哪些事实「该入事实库」由人/业务定，本技能只给判断方法。
  - 不托管密钥：同步脚本若需 API 凭据，从保险库读取，绝不经对话传递（见第八章）。
  - 不保证零错误：来源核实、发布审核仍需人把关。
  - 不自动改写已发布对外物料的法律效力：对外发布走审核流程。
  - 不解决组织协作冲突：跨部门口径分歧需线下对齐，本技能提供「前置对齐」机制而非裁决。
- **范围**：知识库 / 官网 / 公众号 / 文档 / 投标 / 培训材料等内容与知识层；不含底层数据库事务、不含实时系统。

## 二、输入约束与输出承诺

**输入约束**
- 输入形态：自然语言描述（「我们官网和投标书里的产品参数要同步」）、现有文档片段、或一份待整理的事实清单。
- 必需信息：① 哪些事实会变且被多处引用；② 这些事实当前散落在哪里；③ 期望的发布形态（官网/文档/…）。
- 可选信息：现有字段命名、来源链接、生效日期。

**输出承诺**
- 输出形态：Markdown 文本——含三层架构设计、事实库字段模板、5 步 SOP、变更影响清单模板、复盘三问。
- 输出不保证：业务正确性（需人核实来源）、对外物料的法律效力（需审核）。
- 约束/限制：单次聚焦一个内容域；跨域共用事实需在事实库标注 `scope`。不臆造来源，缺来源标「待核验」。

## 四、常见错误与反模式（FAQ + 高频 Q&A）

**反模式（PROHIBITED 预览，详见第七章）**
- ❌ 在内容里直接写死文号/来源值，而非引用事实库。
- ❌ 同一事实在多处复制粘贴，形成「多事实源」。
- ❌ 改了一处忘了其他处，无影响清单。
- ❌ 来源未前置核实就发布，事后才发现错。
- ❌ 把临时草稿当事实库字段，污染唯一源。

**高频 Q&A**
- Q：三层架构适用于小项目吗？
  A：单页面/一次性内容不必。判断标准：事实是否「会变 + 被 ≥2 处引用」。满足才上。
- Q：事实库可以多项目共用吗？
  A：可以，但字段须标 `scope`（如 `medxpert`、`shared`），避免跨项目误用。
- Q：事实变了，旧发布内容怎么办？
  A：先更事实库 → 跑影响清单 → 同步受影响内容 → 对外物料走审核。禁止直接改发布层原文。
- Q：AI 生成内容可信吗？
  A：AI 只按事实库引用生成，事实正确性由来源核实保障；发布前必须人审。
- Q：没有现成同步脚本怎么办？
  A：先用「手动引用 + 变更影响清单」落地机制，自动化是进阶项，非前置条件。

## 五、标准 SOP（步骤表）

| 步骤 | 名称 | 动作 | 产出 | 注意 |
|---|---|---|---|---|
| 1 | 识别 | 列出会变且被 ≥2 处引用的可变事实 | 候选事实清单 | 不把一次性草稿列入 |
| 2 | 建模 | 在事实库建结构化字段，附来源/口径/生效日 | 事实库条目 | 每条有唯一 ID 与 `scope` |
| 3 | 引用 | 内容库/发布层只引用事实 ID，不写死值 | 引用化内容 | 禁止内容内嵌来源原文 |
| 4 | 自动化 | 模板/脚本按事实库拉取生成内容（可选） | 同步脚本 | 凭据从保险库读（第八章） |
| 5 | 影响清单 | 变更事实时列全部受影响内容并统一更新 | 变更影响清单 | 先更源，再同步，后审核 |

## 六、关键事实速查

- **核心思想**：事实只存一处（SSOT），内容声明式引用，改一处全生效。
- **三层**：事实库（源）→ 内容库（半成品）→ 发布层（对外形态）。
- **落地 5 步**：识别 → 建模 → 引用 → 自动化 → 影响清单。
- **复盘三问**：方向前置？核实前置？链路前置？
- **变更顺序**：先更事实库 → 跑影响清单 → 同步 → 审核发布。
- **适用域**：知识库/官网/公众号/文档/投标/培训。
- **禁区**：不托管密钥、不替代决策、不保证零错、不自动赋予法律效力。

---

## 七、铁律（PROHIBITED）

1. 禁止在内容/发布层直接写死可变事实值（文号、参数、状态）——必须引用事实库。
2. 禁止同一事实存在多个「真相副本」（多事实源）。
3. 禁止变更事实后不跑影响清单就直接改发布层。
4. 禁止未经来源核实即发布（来源缺则标「待核验」，不得伪装已核实）。
5. 禁止把同步脚本的 API 密钥/令牌写入对话或技能文件（从保险库读，见第八章）。
6. 禁止用本方法生成具法律效力的原件替代人工签核流程。
7. 禁止把一次性草稿/临时笔记纳入事实库污染唯一源。

## 八、输入输出依赖（凭据从保险库读，不进对话）

- **输入依赖**：用户提供的可变事实清单、现有文档/来源链接、发布形态说明。
- **输出依赖**：事实库 Markdown、SOP、影响清单、复盘模板（纯文本，无外部依赖）。
- **可选自动化依赖**：若用脚本从乐享/Lark/CMS 拉取或同步事实，需要 API 凭据。
  - **铁律**：凭据一律从保险库（如 DPAPI/密钥管理服务）读取，**绝不以明文出现在对话、日志或本文件**。
  - 本技能只描述「读保险库 → 调接口 → 写事实库」的流程，不承载任何密钥值。
- **环境**：无强制运行时；自动化脚本按需选择 Python/Bash，凭据注入走环境变量或保险库 SDK。

## 九、示例

**场景**：MedXpert 官网、公众号、投标书共享「认证口径与状态」。

输入：「认证状态每次更新都要改三处，还漏。」

按 SOP 落地：
1. 识别：候选事实 = `认证口径`、`认证状态`、`生效日期`。
2. 建模（事实库条目）：
   ```markdown
   - id: cert_status
     scope: medxpert
     desc: 产品认证状态
     value: 已获 ISO 13485（待 MDR 审核中）
     source: 质量部 2026-08 通报（待核验链接）
     effective: 2026-08-16
     status: active
   ```
3. 引用：官网/公众号/投标书均写 `{{cert_status}}`，不直接写文案。
4. 自动化（可选）：同步脚本读保险库凭据 → 拉事实库 → 渲染三处页面。
5. 影响清单：变更 `cert_status` → 列出官网/公众号/投标书三处 → 统一更新 → 对外审核。

输出：用户得到事实库模板 + 三处引用化内容 + 变更影响清单，后续只改事实库一处。

## 十、错误处理

| 异常 | 现象 | 诊断 | 恢复 |
|---|---|---|---|
| 来源缺失 | 事实无 `source` | 字段 `source` 为空 | 标「待核验」，退回业务补来源，不发布 |
| 多源冲突 | 同一事实两处值不同 | 出现 ≥2 个 `id` 同义条目 | 合并为单 ID，保留权威来源，其余改引用 |
| 漏改 | 发布层与事实库不一致 | 影响清单未覆盖该处 | 补全影响清单，重跑同步，补审 |
| 同步失败 | 脚本拉取报错 | 保险库凭据失效/接口超时 | 检查保险库凭据有效期，重试；手动兜底更新 |
| 口径分歧 | 跨部门对同一事实定义不同 | 无 `scope`/未对齐 | 线下对齐口径，事实库标注 `scope` 与权威方 |
| 误入草稿 | 一次性内容进了事实库 | `scope` 缺失且永不复用 | 移出事实库，还原为普通内容 |

> 通用原则：错误在「机制层」前置拦截（影响清单 + 来源核实），而非事后救火。无法自动判定时，标「待核验」并交人审，不臆造。
